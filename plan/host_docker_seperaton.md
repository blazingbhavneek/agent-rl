# Host/Docker Separation Plan for `main2.py` + `pipeline/`

This is a surgical plan, not a broad rewrite.

Goal: move the Python harness to the host while keeping `agent.js`, `do_mkmf`,
`make`, `gcc`, `gcov`, `gdb`, and the company shell environment inside the
Docker container. The agent must see a normal production-like filesystem. It
must not see host path prefixes in prompts, generated Makefiles, includes,
coverage paths, `_pipeline_context.json`, or history metadata.

## Key Constraint

Treat the container path as the canonical path.

For a run, the canonical layout should look like the current code already
expects:

```text
/home/seigyo/.../<project_root>/
  src/<process_name>/        # production source, read-only in container
  tests/<process_name>/      # generated tests/traces, writable bind mount
```

The host may store the real source/test output elsewhere, but that must remain
an orchestration detail. Anything generated by the pipeline or shown to the
agent should use only the canonical `/home/seigyo/...` paths.

Because the current code calls `Path.resolve()` all over the place, the safest
minimal rule is:

- Do not use host symlinks that resolve to host-only prefixes.
- Use real directories or bind mounts at the canonical `/home/seigyo/...` paths
  on the host side too, or prepare an attempt workspace there before invoking
  the harness.
- If host and container paths cannot be identical, that becomes a larger
  path-mapping refactor and should not be the first implementation.

This keeps the existing path-heavy code stable and avoids path rewrites through
every prompt, Makefile, coverage checker, and context file.

## What I Verified From The Code

`main2.run()` is the active runtime spine:

1. derive paths from `cfg.source_dir`
2. optionally resume from `test_dir/_pipeline_context.json`
3. `ensure_test_file()`
4. `build_annotated_makefile()`
5. `run_or_load_analysis()`
6. `handle_stubs()`
7. `ensure_minimal_test_runs()`
8. `parallel_generate_unit_tests()`
9. `integrate_all_unit_tests_sequential()`

The summary in `file_progression.md` matches the important disk contract:

- `source_dir` must be directly under a folder named `src`.
- `test_dir` is derived as `source_dir.parent.parent / "tests" / source_dir.name`.
- Most stable output lands under `tests/<process_name>/`.
- The code writes absolute source/test paths into C files, Makefiles, prompts,
  coverage JSON, context JSON, and history files.

## Current Couplings That Matter

### Path derivation

`pipeline/config.py`

- `PipelineConfig.source_dir` is currently both:
  - the path Python reads on the host/process filesystem
  - the path shown to the agent and written into generated artifacts
- `derive_test_dir()` hard-requires `source_dir.parent.name == "src"`.
- `derive_paths()` creates all test paths from that one `source_dir`.

### Source discovery and generated includes

`pipeline/common.py`

- `_project_source_files(cfg)` recursively reads `cfg.source_dir`.
- `_resolve_source_file(cfg, ...)` resolves function metadata against
  `cfg.source_dir`.
- `_source_files_json_for_prompt(cfg)` emits absolute source paths into prompts.
- `_source_includes_for_test_file(cfg, ...)` emits absolute `#include` lines.

`pipeline/stage1_scaffold.py`

- Writes `test_<process>.c`.
- Includes every discovered production `.c` by absolute path.

### Context and Makefile generation

`pipeline/stage2_makefile.py`

- Runs `do_mkmf <test_program>` in `test_dir`.
- Reads `source_dir/Makefile`.
- Writes `test_dir/Makefile`.
- Writes `_pipeline_context.json`.
- Writes these absolute paths into the Makefile/context:
  - `SOURCE_DIR`
  - `SRC_BUILD_DIR`
  - `source_dir`
  - `source_makefile`
  - `actual_source_files`
  - `test_dir`
  - `test_file`
  - `makefile`

### Agent invocation

`pipeline/common.py::run_agent()`

- Writes prompt text to `history_path.with_suffix(".prompt.txt")`.
- Runs:

```text
node <cfg.agent_js> --folder <agent_folder> --prompt-file <prompt_file> --history <history_path>
```

- Default `cfg.agent_js` is `/home/seigyo/rl/agent.js`.
- Defaults for system docs/json also live under `/home/seigyo/rl/...`.
- Snapshots `cfg.source_dir.parent` to undo accidental source edits.

### Build and diagnostics execution

Direct local command execution currently exists at:

- `pipeline/common.py::run_agent()` -> `node`
- `pipeline/common.py::run_make_test()` -> `make test`
- `pipeline/common.py::collect_failure_diagnostics()` -> direct test binary, `gdb`
- `pipeline/common.py::collect_runtime_crash_diagnostics()` -> direct test binary, `gdb`
- `pipeline/stage2_makefile.py::_run_do_mkmf()` -> `do_mkmf`
- `pipeline/stage3_stubs.py::_validate_stub_locally()` -> `gcc`, linked stub binary
- `pipeline/stage6_integrate.py` -> `gcc -fsyntax-only`

Those are the main command boundary points. Most other stages already go
through `run_agent()`, `run_make_test()`, or generated Makefiles.

## Minimal Design

### 1. Keep canonical paths unchanged

Do not make the agent or generated artifacts aware of host mount paths.

Keep passing `source_dir` as the canonical container path, for example:

```text
/home/seigyo/test_env/haiden/dio/dio/src/<process_name>
```

Then the pipeline continues deriving:

```text
/home/seigyo/test_env/haiden/dio/dio/tests/<process_name>
```

This allows different containers to see the exact same source/test path while
their test contents differ because each container gets its own writable bind
mount for `tests/<process_name>`.

### 2. Add one execution boundary

Add a tiny runner module, probably `pipeline/execution.py`, with a function like:

```python
run_command(
    cfg,
    cmd,
    *,
    cwd: Path,
    timeout: int,
    env: dict | None = None,
    shell: bool = False,
) -> CompletedProcessLike
```

Behavior:

- local mode: call `subprocess.run()` exactly like today.
- docker mode: call the command inside the target container.

Docker mode should source the company environment before running commands:

```text
source /home/seigyo/.bash_profile
cd <canonical cwd>
<command>
```

The source step is not optional because `do_mkmf` and company build variables
depend on it.

### 3. Do not add Docker logic to stages

Stages should still say:

```python
run_make_test(test_dir)
run_agent(...)
check_function_coverage(...)
```

Only the helper internals should know whether the command is local or Docker.
That keeps the fragile stage logic intact.

### 4. Start with existing-container mode

Do not introduce full container lifecycle in the first code pass.

First Docker-capable version should assume the container already exists and is
mounted correctly. Add something like:

```text
--execution-mode local|docker
--container-name <name>
--container-profile /home/seigyo/.bash_profile
```

Later, the data-generation orchestrator can create one container per attempt
and pass the container name into this same harness.

## Mount Contract For One Attempt

The host orchestrator should prepare one attempt with these mounts:

```text
/home/seigyo/rl
  same code path on host and container; contains main2.py, pipeline/, agent.js,
  system_functions.json, moove_docs/func.

/home/seigyo/.../<project_root>
  production-like root shown to the agent.

/home/seigyo/.../<project_root>/src
  read-only source tree and all source-side include/lib/object neighbors needed
  by the generated Makefiles.

/home/seigyo/.../<project_root>/tests/<process_name>
  writable bind mount unique to this attempt.
```

If the real project has important includes/libs outside `src`, mount the whole
project root read-only, then mount the attempt-specific test directory writable
over the `tests/<process_name>` location.

Per parallel agent later:

- every container can see the same canonical `src/<process_name>` path
- every container can see the same canonical `tests/<process_name>` path
- the host maps each container's `tests/<process_name>` to a different output
  directory
- after the run, delete the container and keep the mounted test/history folder

## Concrete Code Changes, Kept Small

### Config and CLI

In `pipeline/config.py`, add only execution fields:

```python
execution_mode: str = "local"
container_name: Optional[str] = None
container_profile: Path = Path("/home/seigyo/.bash_profile")
```

In `main2.py::parse_args()`, add:

```text
--execution-mode local|docker
--container-name
--container-profile
```

Default local mode must preserve current behavior.

### New runner helper

Add `pipeline/execution.py` with:

- a small result type or reuse `subprocess.CompletedProcess`
- `run_command(...)`
- careful argument quoting for docker shell execution
- support for:
  - list commands such as `["make", "test"]`
  - shell commands already used for `gcc ... {cflags}`
  - timeout
  - stdout/stderr capture
  - env vars for `MAX_ITERATIONS` and `PYTHON_BIN`

In Docker mode, the command should be executed in the container with the
canonical `cwd`, not a host cwd.

### Replace direct command calls

Minimal replacements:

1. `pipeline/common.py::run_agent()`
   - keep writing prompt/result files where it does now
   - execute `node /home/seigyo/rl/agent.js ...` via `run_command`
   - keep `--folder`, `--prompt-file`, and `--history` as canonical paths
   - in Docker mode, prefer relying on read-only source mount instead of
     snapshot/restore

2. `pipeline/common.py::run_make_test()`
   - replace direct `subprocess.run(["make", "test"], cwd=test_dir, ...)`
     with `run_command(cfg, ["make", "test"], cwd=test_dir, ...)`
   - this means `run_make_test` will need `cfg`
   - or add a tiny compatibility wrapper that reads execution config from cfg
     while keeping call-site churn low

3. `pipeline/stage2_makefile.py::_run_do_mkmf()`
   - run `do_mkmf` via `run_command`
   - preserve the error text

4. `pipeline/stage3_stubs.py::_validate_stub_locally()`
   - run compile, link, and validation binary via `run_command`
   - keep the shell command strings initially to avoid changing flag handling

5. `pipeline/common.py` diagnostics
   - run direct binary and `gdb` through `run_command`
   - preserve fallback behavior when `gdb` is absent

6. `pipeline/stage6_integrate.py`
   - run `gcc -fsyntax-only ...` through `run_command`

### Call-site churn choice

The clean option is to update signatures:

```python
run_make_test(cfg, test_dir, timeout=...)
build_output_with_runtime_diagnostics(cfg, test_dir, test_file, res)
collect_failure_diagnostics(cfg, ...)
collect_runtime_crash_diagnostics(cfg, ...)
```

This touches more call sites but stays explicit and testable.

The lower-churn option is a module-level execution context, but that is more
magical. I would not do that unless the call-site edits become too noisy.

Given this code's fragility, explicit `cfg` is better even if it changes more
lines.

## Agent-Visible Path Hygiene

The agent must only see canonical paths:

- `cfg.source_dir`
- `paths["test_dir"]`
- `paths["test_file"]`
- `paths["makefile"]`
- `source_file_abs`
- `repo_root = cfg.source_dir.parent.parent`
- `/home/seigyo/rl/agent.js`
- `/home/seigyo/rl/system_functions.json`
- `/home/seigyo/rl/moove_docs/func`

Do not mention:

- host checkout path
- host attempt output path
- Docker bind mount source path
- `/run/media/...`
- `/tmp/...` staging paths

Useful guard for implementation:

- In Docker mode, optionally scan each prompt before `run_agent()` and fail if it
  contains known forbidden host prefixes.
- Also scan generated `Makefile` and `_pipeline_context.json` in early smoke
  tests.

## Source Write Protection

Current `run_agent()` snapshots `cfg.source_dir.parent` and restores source
changes after the agent runs.

In Docker mode the better protection is the filesystem itself:

- mount source/project root read-only
- mount only `tests/<process_name>` writable

That is closer to the final production data-generation environment and removes
the need to snapshot a large source tree from the host.

Minimal behavior:

- local mode: keep snapshot/restore as-is
- docker mode: skip snapshot/restore by default and rely on read-only source
  mounts

## What Not To Change In This Pass

Do not change:

- stage ordering
- retry semantics
- prompt wording except path hygiene if needed
- Makefile structure
- analysis behavior
- semantic judge behavior
- parallel data generation
- container lifecycle orchestration
- how unit tests are integrated
- how `_pipeline_context.json` resumes runs

This pass should only introduce the execution boundary and Docker mode.

## Implementation Order

1. Add config/CLI fields with defaults that keep local behavior unchanged.
2. Add `pipeline/execution.py`.
3. Switch `run_agent()` to the runner.
4. Switch `run_make_test()` to the runner and update call sites.
5. Switch `do_mkmf`, stub validation `gcc`, diagnostics, and Stage 6 syntax
   check to the runner.
6. Add prompt/path hygiene guard in Docker mode.
7. Run local syntax/tests to ensure local mode still behaves the same.
8. Run one container smoke test against an already-created container.

## Suggested Smoke Checks

Before a full pipeline run, verify the container has the expected environment:

```text
source /home/seigyo/.bash_profile
command -v node
command -v do_mkmf
command -v gcc
command -v make
command -v gcov
test -f /home/seigyo/rl/agent.js
```

Then run a tiny pipeline slice:

```text
python /home/seigyo/rl/main2.py \
  /home/seigyo/.../<project_root>/src/<process_name> \
  --execution-mode docker \
  --container-name <attempt_container> \
  --max-functions 1 \
  --max-test-attempts 1
```

After it writes files, inspect:

```text
tests/<process_name>/test_<process_name>.c
tests/<process_name>/Makefile
tests/<process_name>/_pipeline_context.json
tests/<process_name>/agent_history/*.prompt.txt
```

They should contain canonical `/home/seigyo/...` paths only.

## Main Risks

1. `Path.resolve()` can leak host paths if the host canonical path is a symlink.
   Use bind mounts or real canonical directories, not symlinks.

2. `_pipeline_context.json` caches absolute paths. If an attempt changes mount
   layout, delete the context or start a fresh output dir.

3. Relative flags copied from `source_dir/Makefile` remain risky. This is
   already true today and should not be mixed into the host/Docker split.

4. Source read-only mounts must still expose `source_dir/linux/*.o` if the
   master Makefile expects those objects.

5. Stage 5 runs unit tests in parallel. For a single container attempt this is
   okay, but later multi-agent work should use separate containers and separate
   writable test mounts per attempt.

6. Diagnostics currently infer master binary/report names imperfectly. This is
   existing behavior and should not be fixed in the same pass.

## Bottom Line

The surgical route is:

- keep `/home/seigyo/...` canonical everywhere
- make host and container see that same path shape
- keep all generated files and prompts container-native
- replace direct subprocess calls with one execution runner
- source `/home/seigyo/.bash_profile` for every container-side command
- leave stage logic alone

That gives the final production-like behavior without asking the fragile CUnit
pipeline to learn a second filesystem model.
